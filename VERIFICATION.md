# Website verification

Deterministic tests are the default delivery gate. Known requirements are encoded as exact assertions and run without model calls or provider credentials. Agents own execution, diagnosis and routine remediation. This document supplies context for those actions; it is not a human checklist.

## Commands

Use `node scripts/pnpm.mjs <pnpm arguments>` for local commands. The launcher selects the installed Node version declared in `.nvmrc` from the current runtime or standard fnm/nvm stores and sets the package working directory without an LLM decision. It fails clearly if that runtime is unavailable; the agent owns remediation. CI already selects `.nvmrc` with setup-node. Use the pinned pnpm. Install root dependencies with `pnpm install --frozen-lockfile` and browser binaries with `pnpm exec playwright install chromium firefox webkit`; TesterArmy's web engine drives the installed Playwright. CI installs browser system dependencies as well. On a host already carrying a Node 24 installation, select that runtime in the command environment rather than tolerating an engine mismatch.

- `pnpm verify` runs type checks, unit/component tests, build, generated-output/HTTP tests, browser tests and verification-report regression tests. It stops on a failure and writes `reports/verification/summary.json` with stage outcomes. Each invocation deletes prior reports before running, so stale success cannot certify a new attempt.
- `pnpm verify:infra` runs type checks and the existing CDK assertion tests, validates their report and writes `reports/verification-infra/summary.json`. Empty, skipped, focused and unsuccessful runs fail this gate too. Install `infra/` dependencies with its frozen lockfile first. It makes no AWS calls.
- `pnpm test:build` builds once and runs output and HTTP checks. `pnpm test:dist` checks an already built site.
- `pnpm test:browser` builds once and runs the browser suite with TesterArmy (`e2e run`). `pnpm exec e2e run --target mobile-chromium` is a focused rerun against an existing build; the gate rejects such partial runs.
- `pnpm test:browser:smoke` builds and runs the browser suite on `desktop-chromium` only, for fast feedback while editing or checking ports. It is not a gate: the validator rejects partial runs.
- `pnpm verify:controls` proves the gate can fail. Against a fresh build it runs each negative control (mutated pinned link, injected page error, deleted local asset, occupied preview port, passing single-target run, missing report) and asserts the exact failure: e2e exit code, executed-test count, error code/message (`ASSERTION_FAILED`, `APP_ALREADY_RUNNING`) and rejection by `scripts/check-test-results.mjs`. A configuration error (`INVALID_CONFIG`, exit 2) fails the script instead of counting as a control. It restores `dist/` byte-identically and writes logs under `reports/controls/`. It takes about 80 s and stays out of `pnpm verify` and CI; run it when changing the browser suite, `e2e.config.ts`, the validator or the TesterArmy version.
- `pnpm test:mutation` remains the existing focused mutation suite for SEO/CSP. It supplements the ordinary gate and is appropriate when changing those contracts.

## Coverage

| Surface | Deterministic evidence |
| --- | --- |
| Every published HTML page | Sitemap-derived cases; one visible H1, exact canonical/OG URL, valid structured data, real image loading, no browser exceptions/local 4xx assets, no horizontal overflow, automated WCAG A/AA rules |
| Homepage | Section navigation, actual project destinations, contact mail link, terminal completion with ordinary motion and content availability with reduced motion |
| Navigation | Homepage → blog → exact pinned article → back; mobile opening/closing, Escape, focus cycling/restoration and body scroll unlock; desktop keyboard activation |
| Every article | Table of contents target navigation, related and adjacent article links, article schema/body, Open Graph image format/dimensions |
| Build/link graph | Internal page, anchor and asset existence across every sitemap page; nonempty unique sitemap covering every built HTML page, exact RSS article membership and LLM discovery links; the robots.txt Sitemap line is checked against the built sitemap index (single line, existing file, same origin as its `<loc>` entries) |
| HTTP surfaces | Homepage/blog and generated images served with correct status/types; discovery/feed endpoints |
| Domain/components/security | Existing unit, Astro Container and SEO/CSP tests retained |
| Infrastructure | Existing CDK assertions and TypeScript checks retained in the separate infra gate |
| Verification itself | Missing/malformed/empty reports, skipped tests, process/report disagreement and browser operational errors cannot return successful verification; interruptions preserve their signal and stop descendant processes |

Browser cases run at 1280px in Chromium, Firefox and WebKit, and at 390px in Chromium and WebKit, plus a 320px Chromium reflow case. All discoverable sitemap pages receive the same page contracts, so newly published posts are included automatically. TesterArmy 0.16 sets viewport size only: the mobile profiles do not emulate touch, `isMobile` or device scale, and this is not a physical-device certification. Without `isMobile`, Chromium no longer widens the layout viewport to fit overflowing content, so the 320px reflow check now measures real overflow.

Browser execution uses one worker and Vitest uses at most two to bound memory on shared hosts and CI. Generated reports are excluded from type-check input. Engine and peer incompatibilities are installation errors. No retry is used to turn a flaky first attempt into success. Focused test execution is forbidden in CI and ordinary runs. Skipped or empty suites invalidate the gate. Assertions can be added as features evolve; the suite does not claim exhaustive defect coverage.

## TesterArmy runner

The browser suite is `tests/e2e/*.e2e.ts`, run by TesterArmy (`e2e` 0.16.0 with `@e2e-dev/web` 0.11.2 on Playwright 1.63.0). `e2e.config.ts` declares the six targets, starts `scripts/preview.mjs` on an OS-assigned port with a strict port (`E2E_PREVIEW_PORT` overrides it, validated as an integer 1024-65535; a bare `pnpm exec e2e run` allocates one itself), and configures no agents, so no test can call a model and no provider credential is read. The gate accepts `reports/browser/report.json` only when it is a `report-1` document whose run passed without errors or exploration, every required target ran every test exactly once in a single passing attempt, no test was unselected, skipped, retried or failed, no step used a model, and model token usage is zero. Failures keep TesterArmy's failure screenshot, screen text and trace under `reports/browser/artifacts/`; read `screen.txt` there for the exact accessible names on the page. `--output` must be a directory inside the project (not the root itself), otherwise `INVALID_CONFIG`.

TesterArmy 0.16 can wait for one matching response but has no public API to observe every page error or response, or to emulate reduced motion. `tests/e2e/targets.ts` therefore reads the attempt's Playwright context through the engine's documented `surfaceOf` escape hatch, only to listen for page errors and 4xx/5xx site responses and to set `prefers-reduced-motion`. These listeners and emulation calls are not recorded as TesterArmy steps or traces; a detected error fails the test in fixture teardown with the collected messages. Every navigation, action and assertion goes through the recorded `app`, `screen` and `browser` fixtures. axe-core runs through `browser.evaluate`. TesterArmy matches accessible names exactly, which is stricter than Playwright's substring default.

TesterArmy allows plain HTTP only on loopback. `patches/e2e@0.16.0.patch` additionally allows exactly the agent-server tailnet address required by the machine's preview policy; CI uses loopback. Revisit the patch when upgrading `e2e`.

## Failure handling and review

Inspect the failing stage and its JSON report, screenshot or trace, reproduce the exact behavior and fix the cause. Use `scripts/preview.mjs` for a preview: on agent-server it binds the tailnet interface, elsewhere loopback; the caller owns shutdown. No port is fixed: the HTTP, smoke-contract and browser suites each take an OS-assigned port per run (`freePort()` in `scripts/preview.mjs`), so gates in parallel worktrees do not collide and need no lock. `scripts/preview.mjs` requires the port as its argument. A port taken between allocation and bind fails startup (`strictPort`) instead of serving from another process; HTTP tests require readiness from their own child process before issuing requests. Static HTML parsing disables resource loading so build contracts do not contact production; browser tests verify actual local assets.

After every production deploy, `deploy.yml` runs `scripts/smoke-production.mjs` against https://friquelme.dev. It waits until `/` is byte-identical to the build just published, waiting up to five minutes because the CDN takes time to propagate. It then checks every sitemap route once, with no retries: status 200, HTML type, exactly one H1, the exact canonical URL, and the exact `cache-control` the publish step sets. It also checks the homepage sections and title, the blog's links to every post, and `rss.xml`, `robots.txt` and `llms.txt`. The homepage's same-origin stylesheets and scripts must return 200 with their content type and the immutable `cache-control`. A failure triggers the rollback described in `AGENTS.md`. The site smoke test deliberately leaves out the CloudFront security headers (CSP, HSTS and the rest). They come from the CDK stack, which is deployed separately, so a site rollback could not repair them, and a correct header change would otherwise roll back a good commit. Checking them after infrastructure deploys is issue #89. `tests/build/smoke-contracts.test.ts` runs the same contracts, without the cache headers that `astro preview` does not send, against the local build in the gate, so a build that passes `verify` cannot trip the production smoke test by its content. Same-origin assets outside `/_astro/` are checked for status only; the homepage currently has none. `tests/unit/publish-site.test.ts` runs `scripts/publish-site.sh` against a stub `aws` and pins its exact sync and invalidation arguments to the smoke test's cache-control constants, so publishing and the smoke test cannot drift apart. A transient CloudFront error during the smoke test still triggers a rollback, because the check is never retried. `scripts/last-good-deploy.mjs` picks the rollback target: the newest successful `deploy.yml` run on `main` other than the current run and commit.

The merge gate adds one deterministic check on top of review: the `review-verdict` commit status (`scripts/review-verdict.mjs`, tested in `tests/unit/review-verdict.test.ts`). It reads the PR's comments and is `success` only when the latest trusted verdict marker for the current head SHA is a PASS. It cannot judge the review's quality, only that a verdict for exactly this head exists. Locally, `scripts/merge-guard.mjs` (tested in `tests/unit/merge-guard.test.ts`) merges only when both gates' `summary.json` files passed on the PR's current head in a clean tree and `evaluate` from `scripts/review-verdict.mjs` returns `success` for that head. It also refuses, with one line per thread naming the bot, file and comment URL, while any inline review thread whose root comment comes from a bot account (`user.type` `Bot` or a login ending in `[bot]`) has no reply from a non-bot user whose association is in `TRUSTED_ASSOCIATIONS`; it checks only that a reply exists, not what it says. Each summary records `git.headAtStart`, `git.headAtEnd`, `git.cleanAtStart` and `git.cleanAtEnd` (`tests/unit/verify-git-state.test.ts`); untracked files that are not ignored count as dirty, and outside a git repository the values are `null`. `tests/unit/review-verdict-workflow.test.ts` pins the workflow's triggers, permissions and base-branch checkout. `tests/unit/ci-workflow.test.ts` pins `.github/workflows/ci.yml`, which produces the required `site` and `infra` checks: triggers, permissions, concurrency, job ids, each job's steps in order with actions compared by name only, and the report uploads. `tests/unit/workflow-coverage.test.ts` fails when any file in `.github/workflows/`, whatever its extension, is not named by its literal path `.github/workflows/<name>` in some other test file under `tests/` or `infra/test/`, so a new or renamed workflow cannot reach review without a contract test. It checks only that such a test exists; whether the test is meaningful is left to review. The ruleset accepts the status only from the GitHub Actions app, so a status set with a personal token does not count. Collaborators remain trusted: anyone who can push a workflow to a branch or comment as the owner can satisfy the check, and `AGENTS.md` forbids doing so without an independent review.

Agent review should check whether acceptance is encoded, whether negative cases fail, and whether verification can silently skip work or accept missing evidence. Review findings must reach the implementing session explicitly. Tests and a reviewer answer different questions; review is still useful where the requirement involves judgment. LLM-based exploration is optional supplemental evidence and findings require reproduction. The model-backed TesterArmy trial in `trials/testerarmy/` (agent journeys, vision assertions, exploration, fault controls and its assessment) is an isolated package with its own lockfile; it is not part of this gate and adds no credential or model dependency to it.

Automated accessibility checks cover detectable rules, not full WCAG conformance. External project destinations are checked as links without contacting third parties or sending messages. Analytics requests are stubbed in browser tests. Against production, agent-server's WebKit cannot load HTTPS (no glib-networking), so run Chromium and Firefox targets only (`--target desktop-chromium,desktop-firefox`). AWS/deployed security and live third-party availability remain outside local browser coverage.
